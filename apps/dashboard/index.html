Documentation

ChaosPay rejoue une panne pendant un achat x402 sur Stellar Testnet, puis compare ce que l’application raconte avec les transferts réellement confirmés sur le réseau.

Principe

Un achat passe par quatre étapes. ChaosPay coupe l’une d’elles, de façon contrôlée, dans un marchand de démonstration.

  1. Le client demande le service et reçoit un défi de paiement (HTTP 402).
  2. Le client signe une autorisation, le facilitator la règle sur Stellar.
  3. Le marchand renvoie le résultat.
  4. Le client confirme la réception par un accusé.

Le verdict ne s’appuie jamais sur la base du marchand seule : les transferts sont relus sur le réseau (hash, actif, payeur, bénéficiaire, montant).

Lire un bilan

Paiement observé
Somme des transferts décodés sur Stellar pour cet achat, frais exclus. En simulation, le paiement est fictif.
Résultat reçu
Réception confirmée par le client logiciel, pas lecture par une personne.
Temps de reprise
Durée entre l’interruption et le résultat retrouvé. Affichée « Non mesuré » quand rien n’a été mesuré.
PASS
Un achat, un règlement attendu, un résultat récupéré.
FAIL
Le client a payé plus que prévu, ou deux achats distincts existent pour une seule intention.
UNKNOWN
Le réseau n’a pas fourni de preuve. Un timeout ou un RPC indisponible n’est jamais converti en échec ni en réussite.
UNSUPPORTED
Le scénario ne s’applique pas à cette application.

Trois sources existent : Simulation (aucun paiement), Testnet (paiement de test réel, preuves vérifiables) et Archive (campagne enregistrée).

Naïf et durable

Le mode durable enregistre l’achat avant d’envoyer le paiement. Après une coupure, il retrouve le même achat et renvoie le résultat sauvegardé. Le mode naïf crée volontairement une nouvelle autorisation au nouvel essai et paie une seconde fois. Ce contre-exemple vient de notre marchand de démonstration. Il ne montre pas une faille de Stellar.

Limites

  • Fixture locale : deux services (CSV et reçus JSON), un actif Testnet, des points de panne explicites.
  • Un troisième service installé depuis le paquet a des preuves historiques ; aucune équipe externe ne l’a encore essayé.
  • Le laboratoire n’écoute que sur 127.0.0.1. Ne pas l’exposer sur Internet ni l’utiliser avec de l’argent réel.
  • Les tests ne sont pas un audit de sécurité et ne garantissent pas un paiement unique universel.
  • Un avis de dépendance connu (Zod) est documenté dans docs/versions.md.

Installation

ChaosPay tourne en local, sur Stellar Testnet. Aucune clé d’IA ni de prestataire financier n’est nécessaire.

Prérequis

Node.js 24 et npm. Un accès réseau au RPC Stellar Testnet et à Friendbot, pour créer et financer les comptes de test.

Lancer le laboratoire

npm ci
npm run setup:testnet
npm run check:connections
npm run dev:dashboard

Ouvrez http://127.0.0.1:3002. Les trois comptes Testnet sont financés gratuitement et le paiement porte sur 0,01 XLM de test. Les clés restent dans .env et .local/, ignorés par Git : ne partagez jamais ce fichier.

Ligne de commande

Pour le client seul, arrêtez le dashboard, puis lancez le facilitator et le marchand chacun dans un terminal.

npm run dev:facilitator
npm run dev:merchant

Dans un troisième terminal, le premier appel est interrompu volontairement, le second récupère le résultat sans second paiement.

npm run smoke:payment -- demo-coupure durable drop
npm run smoke:payment -- demo-coupure durable none

Vérifier

npm run typecheck
npm test
npm run verify:dashboard

Arrêtez d’abord les serveurs lancés à la main. verify:dashboard exécute réellement coupure, redémarrage, concurrence et contre-exemple naïf sur Testnet. Les rapports expurgés sont écrits dans evidence/public/.

Intégrer dans une API

Le kit de reprise est un paquet @chaospay/recovery livré en archive locale. Il n’est pas publié sur npm et reste privé tant que la licence n’est pas choisie.

npm run build:recovery
npm pack ./packages/recovery --pack-destination .local/packages
npm install /chemin/vers/chaospay-recovery-0.1.0.tgz express@5.3.0
import { createPaidRouter } from "@chaospay/recovery/stellar-http";

const paid = await createPaidRouter({
  serviceId: "mon-service",
  port: 3004,
  basePath: "/paid",
  databasePath: "./.local/purchases.sqlite",
  validate: body => body.text,
  produce: text => ({ length: text.length }),
});
app.use("/paid", paid.router);

Routes ajoutées : POST /paid/purchases/:id (défi puis achat signé), POST /paid/purchases/:id/ack (accusé), GET /paid/reports/:id (preuves et verdict), GET /paid/health. L’adaptateur est limité à HTTP en loopback. Guide complet : docs/INTEGRATION_A.md.

Documentation

Lumaid replays a failure during an x402 purchase on Stellar Testnet, then compares what the application reports with the transfers actually confirmed on the network.

The Demo page combines a browser-only educational simulation with the full Testnet recovery lab. The simulation uses fictional amounts and makes no payments. The Testnet lab runs only when the dashboard is installed locally.

Overview

A purchase has four steps. Lumaid deliberately interrupts one of them in a demo merchant.

  1. The client requests a service and receives a payment challenge (HTTP 402).
  2. The client signs an authorization, and the facilitator settles it on Stellar.
  3. The merchant returns the result.
  4. The client acknowledges receipt.

The verdict never relies on the merchant's database alone: transfers are read back from the network (hash, asset, payer, recipient, amount).

Reading a report

Observed payment
Sum of the transfers decoded on Stellar for this purchase, excluding fees. In simulation, the payment is fictitious.
Result received
Receipt confirmed by the client software, not proof that a person read it.
Recovery time
Time between the interruption and recovery of the result. Shown as “Not measured” when no duration was measured.
PASS
One purchase, one expected settlement, and a recovered result.
FAIL
The client paid more than expected, or two separate purchases were made for one intent.
UNKNOWN
The network did not provide proof. A timeout or unavailable RPC is never treated as a failure or a success.
UNSUPPORTED
This scenario does not apply to this application.

There are three sources: Simulation (no payment), Testnet (real test payment with verifiable evidence), and Archive (a saved campaign).

Naive and durable

Durable mode records a purchase before sending payment. After an interruption, it finds the same purchase and returns the saved result. Naive mode deliberately creates a new payment authorization on retry and pays a second time. This counterexample comes from our demo merchant. It does not demonstrate a flaw in Stellar.

Automatic retry and bots

In the “Bug before settlement” Testnet scenario, the runner injects an error before calling the facilitator, then automatically retries with the same purchase ID, request body, and signed authorization. The first attempt does not submit a transaction; the retry can create one real Testnet payment. Nothing is cancelled on-chain.

If a transaction may already have been submitted, its status can be uncertain. The kit checks the facilitator receipt and Stellar evidence and does not blindly create a new authorization. A confirmed on-chain transaction cannot be cancelled; a refund would be a separate transaction.

This approach can be integrated into a bot or agent that pays for APIs, but it is not automatic just by installing this demo. The recovery kit is a private experimental Express package, currently loopback-only and tied to the local facilitator. The bot/client must persist its purchase ID, exact request body, and authorization, and retry with those same values after a lost response or HTTP 202. The dashboard runner implements that retry loop; a separate bot integration still needs its own client logic and testing.

Limitations

  • Testnet fixture: two services (CSV conversion and JSON receipt generation), one Testnet asset, and explicit failure points. The instant browser demo also illustrates market-quote and parcel-tracking requests with fictional data; these do not call live services.
  • A third service installed from the package has historical evidence; no external team has tried it yet.
  • The lab listens only on 127.0.0.1. Do not expose it to the internet or use real money.
  • These tests are not a security audit and do not guarantee universal single-payment behavior.
  • A known dependency advisory (Zod) is documented in docs/versions.md.

You do not need to install anything, create an account, or connect to Stellar to see how recovery works.

Open the instant demo →

The browser demo uses fictional examples only. It sends no network requests and makes no payments. When you are ready to develop locally or test real Testnet transactions, open the optional setup below.

Connect your own AI agent

The goal is to recover interrupted paid API requests from agents on your computer. Installing the lab does not automatically connect your existing agent.

  1. The API provider integrates the server recovery kit to retain purchase state and results.
  2. Your agent client securely stores the purchase ID, exact request and original signed authorization.
  3. After an interruption, the client reuses those values, verifies the result and acknowledges receipt. Unknown payment states require further evidence.

Available today: an experimental server package installed from a local archive and a recovery CLI for saved lab purchases. Still to build: a supported agent connector across languages and frameworks without manual Node.js setup.

Server integration guide

Set up the local lab (optional)

Windows provides a double-click launcher with a portable runtime. Linux and macOS use the developer setup below. Testnet configuration is a separate step.

Windows: download, extract, launch

No separate Git, Node.js or npm installation is required.

  1. Download the project ZIP and extract the entire folder.
  2. Double-click Lancer-Lumaid.cmd. The first launch downloads a portable runtime and installs dependencies. Internet is required.
  3. Your browser opens at http://127.0.0.1:3002. Keep the terminal open; Ctrl+C stops the server.

For Testnet, stop the server, run Configurer-Testnet.cmd, then launch Lumaid again. Existing credentials are preserved. Requires Windows 64-bit. If port 3002 is occupied, close the previous server.

Installation guide

Linux setup

In Bash, install Node Version Manager (nvm):

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash

Open a new terminal, install Node.js 24, then clone the project and start the simulation:

nvm install 24
nvm use 24
git clone https://github.com/nielslecodeur/Lumaid.git
cd Lumaid
npm run quickstart

macOS setup

Install Node Version Manager (nvm) from Terminal:

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash

Quit and reopen Terminal, install Node.js 24, then clone the project and start the simulation:

nvm install 24
nvm use 24
git clone https://github.com/nielslecodeur/Lumaid.git
cd Lumaid
npm run quickstart

Open http://127.0.0.1:3002 and select Simulation. This path requires no Testnet setup and makes no payment. On Windows, stop the server and use Configurer-Testnet.cmd. For the developer installation, stop the dashboard and run npm run setup:testnet, then npm run check:connections and restart with npm run dev:dashboard. Testnet runs submit real test-network transactions; confirmed transactions cannot be cancelled. Credentials stay in .env and .local/. Never share these files.

Command line

To run the client on its own, stop the dashboard, then start the facilitator and merchant in separate terminals.

npm run dev:facilitator
npm run dev:merchant

In a third terminal, the first call is deliberately interrupted; the second recovers the result without a second payment.

npm run smoke:payment -- demo-coupure durable drop
npm run smoke:payment -- demo-coupure durable none

Verify

npm run typecheck
npm test
npm run verify:dashboard

Stop any manually launched servers first. verify:dashboard runs interruption, restart, concurrency, and the naive counterexample on Testnet. Redacted reports are written to evidence/public/.

Integrate an API

The recovery kit is an @chaospay/recovery package delivered as a local archive. It is not published on npm and remains private until a license is chosen.

npm run build:recovery
npm pack ./packages/recovery --pack-destination .local/packages
npm install /path/to/chaospay-recovery-0.1.0.tgz express@5.3.0
import { createPaidRouter } from "@chaospay/recovery/stellar-http";

const paid = await createPaidRouter({
  serviceId: "my-service",
  port: 3004,
  basePath: "/paid",
  databasePath: "./.local/purchases.sqlite",
  validate: body => body.text,
  produce: text => ({ length: text.length }),
});
app.use("/paid", paid.router);

Added routes: POST /paid/purchases/:id (challenge, then signed purchase), POST /paid/purchases/:id/ack (acknowledgment), GET /paid/reports/:id (evidence and verdict), and GET /paid/health. The adapter is limited to loopback HTTP. Full guide: docs/INTEGRATION_A.md.

The server kit makes repeat requests recoverable; it does not retry a disconnected client's request for it. A bot must securely persist the original purchase ID, request body, and signed authorization, then retry with exactly those values. Do not create a new authorization while the prior submission may be unknown: a confirmed Stellar transaction cannot be cancelled, and a refund is a separate payment.
